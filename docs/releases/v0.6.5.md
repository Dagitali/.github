# Dagitali GitHub Defaults v0.6.5

Version 0.6.5 updates Python fixture build and development tooling. This patch-release record is
dated 2026-10-07 (America/New_York). Tag and publication dates have not been independently verified.

- Version identifier: `v0.6.5`; this record does not verify tagging, release approval, or publication.
- Comparison baseline: the local [v0.6.4] tag. Before release-document preparation, the only source
  differences were three dependency requirement changes across two fixture configurations.
- Validation identity: results below concern the release-preparation worktree, not a subsequent tag.

## Highlights

See the [changelog] for this version's concise change list.

## Change Scope

Raise `build-system.requires` from `setuptools>=75` to `setuptools>=84.0.0` in
`tests/fixtures/python/pyproject.toml` and `tests/fixtures/python-cdk/pyproject.toml`. Update the
Python fixture's development mypy pin from 1.15.0 to 2.4.0. The build backend, runtime dependencies,
Python requirements, Ruff/pytest pins, and test configuration remain unchanged.

No workflow declarations, public composite actions, starter templates, community defaults, hosted
settings, or root validation dependency requirements change. Release documentation adds this record
and updates the archive and changelog.

## Compatibility and Configuration

No shared workflow/action interface changes or new deprecations. Consumer projects retain control of
their own dependencies; no caller rewrite or copied-starter migration is required. See [workflow
contracts] for the public surface.

Fixture builds now require setuptools 84.0.0 or newer rather than 75 or newer; this is a minimum,
not an exact pin or upper bound. The Python fixture's development environment selects mypy 2.4.0.
Existing fixture environments must be refreshed deliberately to exercise the new requirements. Local
root checks do not establish fixture build compatibility or the upgraded checker's behavior inside
an independently installed fixture environment.

## Support Boundary

No declared runtime or platform support expansion. Both fixtures retain their Python requirement;
the higher build-tool minimum applies only to their build environments, not to consuming projects.
The library remains non-publishing and non-deploying.

- Scope inspection on 2026-10-07: the clean pre-preparation checkout differed from local v0.6.4 in

- Local preparation gate: Passed `make check release-changelog RELEASE_VERSION=0.6.5` on 2026-10-07

  update. Ruff lint/format, actionlint, automation contracts, strict mypy, all 127 pytest tests,
  local Markdown links, and the dated changelog check passed.
- Refreshed fixture installation, isolated builds, fixture mypy execution, and CDK synthesis: Not

- Hosted CI, manual candidate matrices, and representative consumer callers: Not run or inspected
  during preparation; no hosted workflows were dispatched.
- Tagged-revision validation: Not verified; no local v0.6.5 tag existed at scope inspection.

Use the [testing guide] and [release policy] for final-revision checks. Preparation results must not
be attributed to a later commit or tag.

## Artifact Contracts

No artifact contract changes. Package, diagnostic, audit, and inventory declarations retain their
existing names, formats, retention, upload conditions, and returned metadata. Builds with the
updated fixture requirements remain unverified; see [Validation](#validation).

## Publication, Adoption, and Rollback

Shared tagging and publication rules are in [release operations].

Tagging, GitHub Release publication, and consumer adoption are not verified for v0.6.5.
Documentation preparation performs no tags, pushes, publication, deployment, or hosted settings
changes. Library validation does not publish consumer packages or deploy infrastructure.

No consumer dependency rollout is required for these fixture-only changes. Maintainers should verify
fresh fixture installs and builds before treating the updated requirements as tested. A fixture
regression can be addressed by restoring the previous requirement through a reviewed follow-up
change. Consumer reference rollback restores each caller's previously verified immutable revision;
[v0.6.4] is the comparison baseline, not proof of a universally known-good target.

## Known Limitations and Follow-Up

The maintainer should verify refreshed fixture environments and reconcile final-revision and hosted
evidence with [Validation](#validation), recording release approval and verified tag/publication
outcomes separately from released-version wording.
