# Dagitali GitHub Defaults v0.6.1

Version 0.6.1 updates pre-commit maintenance tooling without changing shared automation contracts.
This patch-release record is dated 2026-10-07 (America/New_York). Tag and publication dates have not
been independently verified.

- Version identifier: `v0.6.1`; this record does not verify tagging, release approval, or
  publication.
- Comparison baseline: the local [v0.6.0] tag. Before release-document preparation, the only source
  difference was two hook revision updates in `.pre-commit-config.yaml`.
- Validation identity: results below concern the release-preparation worktree, not a subsequent tag.

## Highlights

See the [changelog] for this version's concise change list.

## Change Scope

The pre-commit configuration updates Commitizen from v4.18.1 to v4.19.1 and md-toc from 9.0.0 to
9.1.0. Hook IDs, arguments, stages, file selection, and the remaining tool revisions are unchanged.
Release documentation adds this record and updates the archive and changelog.

No workflows, public actions, starter templates, community defaults, validation requirements,
runtime matrices, permissions, or hosted settings change.

## Compatibility and Configuration

No shared workflow/action interface changes or new deprecations. No consumer caller rewrite,
reference update, or copied-starter migration is required for these checkout-local hook updates.
Maintainers using pre-commit receive the updated tool environments when running the configured
hooks; the configuration itself does not install hooks. Upstream tool behavior has not been
independently exercised in this preparation. See [Validation](#validation) for the evidence
boundary.

## Support Boundary

No support-boundary changes. The updates concern repository maintenance tools, not consumer runtime
dependencies or new runner/platform support.

## Validation

Interpret these results using the [evidence boundaries] and [reading guide].

- Scope inspection on 2026-10-07: the clean pre-preparation checkout differed from local v0.6.0 only
  in `.pre-commit-config.yaml`, with the two revision changes described above.
- Local preparation gate: Passed `make check release-changelog RELEASE_VERSION=0.6.1` on 2026-10-07
  with Python 3.14.7 and Popo 0.5.2 against the release-preparation worktree before this evidence
  update. Ruff lint/format, actionlint, automation contracts, strict mypy, all 127 pytest tests,
  local Markdown links, and the dated changelog check passed.
- Updated Commitizen and md-toc hook execution: Not run; ordinary repository checks do not install
  or execute these pre-commit environments, and potentially modifying hooks were not invoked.
- Tagged-revision validation: Not verified; no local v0.6.1 tag existed at scope inspection.
- Hosted CI, manual candidate validation, and representative consumer callers: Not run or inspected
  during preparation; no hosted workflows were dispatched.

Use the [testing guide] and [release policy] for final-revision checks. Preparation results must not
be attributed to a later commit or tag.

## Artifact Contracts

No artifact contract changes. Hook revision updates do not introduce a package distribution or alter
workflow diagnostics, audit/inventory outputs, upload conditions, or retention.

## Publication, Adoption, and Rollback

Shared tagging and publication rules are in [release operations].

Tagging, GitHub Release publication, and consumer adoption are not verified by this record.
Documentation preparation performs no tags, pushes, publication, or hosted configuration changes.
Library validation remains non-publishing and never deploys consumer infrastructure.

No consumer rollout is required for checkout-local hook updates. If a hook regression is discovered,
maintainers can restore its previous revision through a reviewed follow-up change and rerun affected
checks. [v0.6.0] is the comparison baseline, not proof of a universally known-good consumer target.
Existing immutable tags remain unchanged.

## Known Limitations and Follow-Up

The maintainer should exercise the updated hook environments and reconcile final-revision and hosted
evidence with [Validation](#validation), recording release approval and verified tag/publication
outcomes separately from released-version wording.
