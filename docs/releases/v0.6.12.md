# Dagitali GitHub Defaults v0.6.12

Version 0.6.12 aligns generic issue forms with Popo, enables blank issues, and improves bug-report
context while preserving optional classification and affected-project support/security navigation.
This community-default maintenance patch leaves shared automation contracts unchanged.

- Version identifier: `v0.6.12`.
- Record date: 2026-10-07 (America/New_York), identifying documentation preparation rather than a
  verified tag or publication date.
- Comparison baseline: the local v0.6.11 tag; scope includes committed issue-form/test changes and
  accompanying documentation and release records in the preparation checkout.
- Validation identity: preparation-checkout results, not tagged-revision evidence.

## Change Scope

The [issue chooser] enables blank issues for reports outside the structured forms, retaining its
support and security-policy links. The [bug form] adds a required version/commit input, makes the
existing environment field required, and explicitly accepts unknown/not-applicable responses. An
optional installation/invocation field separates setup context from runtime details. Its generic
reproduction outline covers installation, configuration, execution, and observed results; summary
wording invites actual behavior without adding a second required observation field.

The [feature form] invites concrete, user-facing needs with problem-to-solve and proposed-outcome
wording, retaining observable outcomes and compatibility/security/cost context. The [documentation
form] clarifies concerns, corrections, and supporting evidence with a repository-neutral example,
and explicitly tells uncertain reporters they may leave impact classification blank. Product-neutral
maintainer guidance aligns triage, evaluation, actionable documentation corrections, and reporting
navigation with their respective responsibilities. Form names use title case. Existing field IDs,
GitHub labels, bracketed title prefixes, and optional classification selectors remain. These final
prompt refinements add no mandatory fields or checkboxes.

The README and contributor guide describe these defaults. Regression coverage protects required
responses, optional selectors/installation information, prefixes, and private reporting routes. No
reusable workflows, composite actions, starters, dependencies, fixtures, or hosted settings change.
Separate pending Popo caller work is not part of this library release or proof of adoption.

## Compatibility and Configuration

Issue submission behavior changes: bug reporters must complete version and environment fields,
using unknown/not-applicable responses when appropriate. Existing field IDs remain, with new
`version` and `installation` fields. Integrations interpreting form responses should review those
additions and the updated displayed labels. Feature surface and documentation impact stay optional.
Blank issues now bypass the structured forms; they are not a private reporting channel.

Public workflow/action paths, inputs, outputs, permissions, runner requirements, required-check
identities, and artifacts remain unchanged. No automation caller migration or dependency reinstall
is required. Local consumer issue-template configuration still replaces the entire inherited set;
consumers retaining overrides must review their own policy rather than assume these changes apply.

## Support Boundary

No support-boundary changes. Forms remain product-neutral, with platform-specific context requested
only where relevant. Chooser links guide users to the affected project's policies; they do not
establish monitored recipients or private vulnerability-reporting enablement.

## Publication, Adoption, and Rollback

Shared tagging and publication rules are in [release operations].

Released wording is prepared at the maintainer's request; tagging and GitHub Release publication are
not verified. Inheriting consumers observe the organization defaults from the default branch, not an
immutable workflow pin. Updating a workflow reference does not select an issue-form version.
Consumers with local forms/configuration retain their overrides; no consumer files are removed.

If the new issue behavior needs correction, use a reviewed forward fix or revert the relevant
default declarations to the v0.6.11 baseline without retargeting tags. Reverting shared defaults
affects inheriting consumers, so review that scope separately from automation rollback.

## Known Limitations and Follow-Up

Maintainers should verify the displayed chooser and bug-form validation after integration, and check
a consumer without local issue-template overrides. Preserve unknown/not-applicable responses and
optional classification during that review. See [Validation](#validation) for outstanding hosted
evidence; no successful consumer adoption is inferred from local tests.
