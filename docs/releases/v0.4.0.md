# Dagitali GitHub Defaults v0.4.0

Version 0.4.0, tagged locally on 2026-10-05 (UTC-04:00), improves community defaults and consumer
adoption of shared automation. This minor release was prepared as a candidate on 2026-10-05 on
`release/0.4.0`. The results below preserve that preparation checkout, not evidence of final-tag
validation or GitHub Release publication.

- Status: local annotated `v0.4.0` tag verified on 2026-10-06; its metadata records
  `2026-10-05T14:45:43-04:00`. Remote availability and publication remain unverified here.
- Tag: `v0.4.0`; preparation-time tag absence is historical, not current status.
- Preparation base: the merge of `feature/reconcile-release-documentation` into `develop`, plus
  the release-documentation updates prepared on `release/0.4.0`.

v0.3.0 draft. It also corrects [v0.3.0]'s record and changelog to describe the actual

The detailed change categories below were moved intact from the maintained changelog. They describe
candidate change scope, not evidence of hosted validation or publication.

- Add affected-project security/support routing and a default private vulnerability form without

## Compatibility and Configuration

No reusable workflow/action paths, inputs, defaults, outputs, runner requirements, permissions, or
artifact contracts are changed by the tagged comparison against v0.3.0. The breaking publishing
removal and GitHub.com-only Python/CDK composition belong to v0.2.0, not this release. A comparison
of the tagged tree against v0.3.1 also confirms unchanged workflow/action declarations. This scope
comparison does not establish completion of historical release-approval gates.

Consumers adopt the new starters explicitly, replace SHA placeholders with a reviewed available
revision, and configure project-specific inputs. PR dependency review is not a merge-queue
prerequisite; manual inspection is optional evidence. Copied callers need separate edits from
library SHA updates. Review local community-policy overrides because inherited defaults may not
apply.

## Support Boundary

Existing runtime and platform boundaries remain unchanged; see [workflow contracts]. Python/CDK
same-revision action composition requires GitHub.com, Swift CI targets Swift Package Manager, and
CDK checks do not deploy or perform credential-dependent lookups. Installation executes project
code; inspection must run trusted revisions without secrets. Configurable environments and committed
policies are not proof of hosted compatibility or effective enforcement.
