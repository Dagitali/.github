# Dagitali GitHub Defaults v0.2.0

Version 0.2.0, tagged on 2026-10-05, hardens shared GitHub Actions and adds isolated dependency
inspection, consumer-owned release automation, and library validation tooling. This retrospective
record was prepared on 2026-10-05 from local Git history. The annotated `v0.2.0` tag records
`2026-10-05T00:41:43-04:00` and resolves to commit `cf1a679ad735be2c118b724461cbc0564878d889`, the
merge of `release/0.2.0`. The tag's recorded date is not a verified publication date.

## Highlights

- Harden shared workflows with immutable remote-action pins, deny-by-default token permissions,
  job-scoped read access, and checkout without persisted credentials.
- Compose Python/CDK workflows from shared actions at the workflow's running revision. Add generic
  cache selection, setup-only support, input guards, environment reporting, and optional
  diagnostics.
- Strengthen Python package validation with fresh-output guards, metadata checks, clean wheel/sdist
  installation, optional smoke commands, and validated artifact metadata outputs.
- Add optional isolated Python dependency auditing and validated CycloneDX inventories, including
  configurable inspection tooling, compatibility constraints, and failure-aware evidence.
- Add library CI, manual non-publishing candidate validation, credential-free consumer fixtures,
  pytest regression coverage, and Popo v0.4.1-backed contract/actionlint validation.
- Add Make setup/check/format targets, pinned lint/type tools, repository ownership guidance,
  dependency maintenance, consumer-owned release starters, and maintenance/release documentation.

### Breaking Changes

- Refactored Python/CDK CI uses GitHub.com's same-revision `$/` action references, which are not
  supported on GitHub Enterprise Server; consumers on that platform must retain an earlier revision.
- Remove reusable `python-publish.yml`; migrate to the consumer-owned Python release template for
  PyPI trusted publishing. Shared validation workflows do not receive publishing identity.

## Compatibility and Configuration

Two breaking boundaries require explicit consumer review:

1. Python/CDK workflows use GitHub.com's same-revision `$/` action references. These declarations
   are not supported on GitHub Enterprise Server; retain an earlier suitable revision there.
2. Reusable `python-publish.yml` is removed. Migrate to the consumer-owned Python release starter:
   the shared builder validates packages, while the consumer configures its protected publishing
   environment, trusted identity, and publication job. Library validation never publishes packages.

Python CI defaults change from 3.12/3.13 to 3.13/3.14; choose the consumer's actual supported
matrix. Review cache inputs, installation commands, diagnostics, package output contracts, and
runner requirements before updating references. Command inputs execute trusted project code, not
sandboxed code. The Python CDK starter enables Ruff/pytest checks; consumers must provide those
tools.

Copied starters need separate consumer edits: replace release-SHA placeholders with an independently
validated revision, update triggers and permissions, and review release artifact download names.
Changing a library SHA does not automatically update copied callers or configure hosted rules.

## Support Boundary

Declared defaults include Ubuntu Python CI/package checks, Python 3.13/3.14 CI, Node 22/Python 3.13
CDK setup, and Swift Package Manager on `macos-15`. CDK synthesis must work without AWS credentials
or account lookups; Swift package checks are not signed Xcode application release automation.
Configurable alternatives are not proof of hosted-tested support. Read the [workflow contracts] at
the tagged revision; current guides may evolve independently.

## Artifact Contracts

The package workflow declares `python-dist` with seven-day default retention, fresh wheel/sdist
validation and clean installations before success-only upload. It exposes artifact ID, authenticated
URL, and archive digest; consumers overriding the artifact name must update download expectations.
Diagnostic paths are opt-in, with configurable names/retention and runtime/runner suffixes where
declared. Inspection workflows retain separate audit/inventory evidence and distinguish missing or
failed reports from clean results. Review the tagged YAML for exact conditions and overrides.

Artifact production, content, retention enforcement, and availability at release time are not
verified here. Neither diagnostics nor an installed-environment inventory constitutes a published
release or a vulnerability-free attestation.
